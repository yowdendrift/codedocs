# Content model

Everything the viewer shows and the tool checks comes from this model. Follow it exactly.

## Layout

```
<docs folder>/                 usually docs/, or docs/codebase/ if docs/ is already used
  index.html                   viewer         (built into the binary, replaced on upgrade)
  viewer.css                   layout         (built into the binary, replaced on upgrade)
  lib/                         only with install-viewer --offline: the viewer's libraries
  theme.css                    look           (yours, edited by /codedocs style, never replaced)
  docs.config.json             settings       (project, editor, ignore, last_synced, skill_version)
  manifest.json                generated by `codedocs manifest`; never edit by hand
  content/
    overview.md                the bird's-eye view: always exists
    glossary.md                the project's nouns
    gotchas.md                 traps and non-obvious rules
    topics/<slug>.md           one per subject someone asked to have documented (/codedocs add)
    components/<slug>.md       one per major component (structure)
    flows/<slug>.md            one per important journey through the code (behaviour)
    concerns/<slug>.md         one per cross-cutting pattern (errors, state, threading, …)
    decisions/NNNN-<slug>.md   one per significant decision (why it's like this)
    changes/YYYY-MM-DD-<slug>.md  saved explanations of changes (/codedocs explain)
```

Slugs are lowercase kebab-case. Component slugs are how other pages refer to components, so keep
them short and stable (`timeline`, `render-pipeline`, `media-library`).

## The two views and how they link

- **Structure** (components) answers *where does this live and what is it for*.
- **Behaviour** (flows) answers *how does this happen*.
- **Concerns** are patterns that apply everywhere and aren't a journey.
- **Decisions** pin the *why* onto either view.

Cross-links are declared **once**, on the flow, concern or decision, with `components: [...]`.
The tool computes the reverse direction (which flows pass through a component) and the viewer
shows both. Don't maintain "Flows through here" lists by hand.

## Frontmatter

Simple `key: value` lines between `---` markers. Lists use `[a, b]` on one line. No nested YAML.

Every page:

```
---
title: Render pipeline
summary: One sentence a newcomer can understand. Shown under the title and on cards.
order: 20                     # optional; sort order within its kind (lower first)
generated_with: 0.1.0         # skill version that wrote it (codedocs version)
updated: 2026-10-28
locked: false                 # true = humans own this page; never rewrite it
---
```

Extra keys per kind:

| kind | extra keys |
|---|---|
| component | `paths: [src/render/**, src/workers/encode*.ts]`: globs for the code this component owns. Required; the tool uses them for change mapping and coverage. A file should belong to exactly one component. |
| flow | `components: [ui, timeline, render-pipeline]`: in the order the flow visits them |
| concern | `components: [...]`: where the pattern applies |
| topic | `components: [...]`: components the subject spans; `audience: admin`, `developer` or `both` |
| decision | `components: [...]`, `status: stated` (the user told you) or `status: inferred` (you reconstructed it) |
| change | `components: [...]`, `range: abc123..def456` |

The `kind` comes from the folder; don't set it.

## Code references

Write references to code as inline code, repo-relative, forward slashes. The viewer turns them
into links that open the editor at the right line; the tool checks they still exist.

| form | use for |
|---|---|
| `` `src/render/queue.ts` `` | a whole file |
| `` `src/render/queue.ts#RenderQueue` `` | **preferred**: a symbol. Survives edits; the tool resolves the current line. |
| `` `src/render/queue.ts#RenderQueue.enqueue` `` | a method or nested symbol |
| `` `src/render/queue.ts:42` `` / `` `:42-60` `` | a specific spot with no good symbol. Line numbers go stale; use sparingly |

A reference must be a real path. Don't wrap generic names (`package.json` meaning "a package file")
or pseudo-paths in backticks.

## Links between pages

Normal relative markdown links to the `.md` file, optionally with a heading anchor:
`[the timeline](../components/timeline.md)`, `[step 3](../flows/export.md#3-encode)`.
Heading anchors are the heading text lowercased, punctuation removed, spaces as hyphens.

## Callouts

```
> [!NOTE]      background worth knowing
> [!TIP]       a useful way in
> [!WARNING]   easy to get wrong
> [!CAUTION]   will break something
> [!INFERRED]  reconstructed from the code, not confirmed: say what the evidence is
> [!INSIGHT]   something the user told you (/codedocs add): shown as "From the team".
               Never remove or reword one when rewriting a page.
```

For a single inferred claim inside a sentence, end it with `(inferred)`; the viewer tags it.

## Diagrams

Use ```` ```mermaid ```` blocks. Keep each diagram small enough to read without zooming (about
12 nodes at most). Prefer:

- `flowchart LR` for the component map in the overview,
- `sequenceDiagram` for a flow's overview (participants = components),
- `stateDiagram-v2` when something has real states (a render job, a project's dirty/saved state).

A diagram supports the prose; it never replaces it. Label edges with verbs ("reads", "posts job to").
Keep labels plain: no parentheses, quotes or semicolons inside unquoted node labels.

## Page templates

Section headings below are the defaults. Drop a section when it would be empty; never pad.

### overview.md

```
---
title: <Project name>
summary: What this software is and who uses it, in one sentence.
---
# <Project name>

## What it does
2–4 sentences, from the user's point of view.

## How it fits together
One mermaid flowchart of the components and how they talk, then one short paragraph per
component in plain words, each linking to its page.

## Main journeys
A bullet per flow: one sentence and a link.

## Rules that always hold
The invariants: things that must stay true for the system to work. Each one short, with a link
to where it's enforced. (These are the most valuable lines in the docs.)

## Running it
How to install, run, test, build. Real commands.

## Reading guide
Where to start for common goals: "to change how export works, read …", "to add a new effect …".
```

### components/<slug>.md

```
---
title: Render pipeline
summary: Turns the timeline into frames and encoded video, off the UI thread.
paths: [src/render/**]
---
# Render pipeline

## Responsibility
What this component is for, and just as important, what it is *not* responsible for.

## How it works
The mental model in prose: the main idea, the key data structures, the lifecycle. Short.

## Parts
### <Sub-part name>
2–5 sentences per part: what it does, its key types/functions as code refs.
(Level 2 of the structure view. The map shows these headings.)

## Interfaces
What other components call, what it calls out to, the data shapes that cross the boundary.

## State and data
What it owns, where that lives, who else can change it.

## Watch out for
Component-specific gotchas. Link to gotchas.md entries if shared.
```

### flows/<slug>.md

~~~
---
title: Exporting a video
summary: From pressing Export to a finished file on disk.
components: [ui, timeline, render-pipeline, encoder]
---
# Exporting a video

## In short
3–5 sentences: trigger, the hops, the outcome.

```mermaid
sequenceDiagram
  participant UI
  participant Timeline
  ...
```

## Step by step
### 1. <Step name>
Which component, what happens, which function: code ref. Data passed on.
### 2. …

## When it goes wrong
Errors, cancellation, partial results: where they are handled.

## Things to know before changing it
~~~

Overview level = "In short" plus the diagram. Detailed level = "Step by step" with code refs.

### topics/<slug>.md

A subject that spans the structure: the entry point for someone who asks "how does X work
here?". It ties components, flows and settings together and links out to them; it doesn't
repeat them. Sections depend on `audience`:

~~~
---
title: Payments
summary: Taking money for account upgrades, from checkout to the upgrade being applied.
audience: both
components: [payment, user-upgrade]
---
# Payments

## What it does                  (admin, both) plain words, no code
## How it fits together          (all) one diagram: the parts and outside services involved
## Setting it up                 (admin, both) where in the software it's configured, the options that matter
## What can go wrong             (admin, both) symptom → likely cause → where to look (logs, settings)
## Under the hood                (developer, both) the flows and components, with links; key classes as refs
## Extending it                  (developer, both) the supported extension points
## Related                       links to flows, decisions, gotchas
~~~

### concerns/<slug>.md

```
## The pattern       how it's done here, with a code example ref
## The rule          what new code must do
## Where it applies  components, with links
## Exceptions        places that break the pattern, and whether that's deliberate
```

### decisions/NNNN-<slug>.md

```
---
title: Render on a worker thread
status: inferred
components: [render-pipeline]
---
## Context        what problem forced a choice
## Decision       what was chosen
## Alternatives   what else was possible, and why not (mark inferred reasoning)
## Consequences   what this makes easy, what it makes hard
## Evidence       for inferred decisions: what in the code suggests this
```

### glossary.md

A definition list as a table: `| Term | Meaning | Where |`. One plain sentence per meaning, a code
ref in "Where". Alphabetical. Include the project's own terms and any domain terms a developer
new to the field would trip on.

### gotchas.md

One `##` per gotcha: the trap in the heading ("Clips are mutated in place during preview"),
then why it's a problem and what to do instead, with code refs.

### changes/YYYY-MM-DD-<slug>.md

Written by `/codedocs explain`. See `explain.md` for the structure.
